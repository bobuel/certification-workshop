# Certification Workshop

Start with the user's concrete program and requested result. New program -> certification-setup. Existing program -> read its current program.json, brief, decision register and last action before proposing work. Never require an existing exam to begin.

Route by need: role/tasks/SME instruments -> certification-job-analysis; blueprint/methods -> certification-blueprint; questions/practical tasks/rubrics -> certification-items; expert feedback -> certification-review; pilot data/passing-standard work -> certification-pilot; exam forms/candidate guide/delivery -> certification-launch; awards/appeals/results -> certification-operations; changes/renewal/retirement -> certification-maintenance. Load only the relevant specialist.

Read [operating contract](references/operating-contract.md) before changing program records; use [records](references/records.md) for fields and [helpers](references/helpers.md) for deterministic work. [Program development method](references/method.md) supplies the end-to-end approach. [Templates](assets/templates.md) provide substantive starting artifacts. Maintain a useful summary: confirmed decisions, evidence missing, active work, dependencies, owners, next action. Advance drafting while external evidence is pending; do not fabricate that evidence or demand every lifecycle stage for a narrow request.

For the actual workflow, create the requested artifacts rather than merely listing future steps. Resolve routine technical choices. Ask only for consequential unresolved program decisions; existing authorization persists. Show the difference between a draft, reviewed artifact, approved release and observed external result. Work in the user's program folder, never the installed plugin. Resume from records, not assumed chat memory. Use [continuity and handoff](references/continuity.md) for source preservation, historical results, fresh-session work and verified archive/restore.
